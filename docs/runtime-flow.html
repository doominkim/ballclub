SessionStart에서 갈라지는 두 경로

Bootstrap과 업데이트는 같은 이벤트를 쓰지만 책임과 출력이 분리돼.

작업 경로 · 매 세션 문맥 준비

  1. startup, clear, compact에서만 라우터 skill을 읽어.
  2. superpowers-lite:bootstrap marker와 최소 규칙을 주입해.
  3. resume은 기존 문맥을 재사용하므로 bootstrap을 중복 주입하지 않아.

관리 경로 · 업데이트 확인

  1. 새로운 startup에서만 하루 한 번 원격 버전을 확인해.
  2. 새 버전이 있을 때만 자연스러운 영어로 업데이트 여부를 물어.
  3. 명시적 승인 후 네이티브 updater를 실행하고 현재 세션을 종료해.
분리 원칙

업데이트는 플러그인 생명주기라서 skill 목록에 들어가지 않아. Hook은 질문과 승인 경계만 전달하고, 실제 변경은 deterministic script가 수행해.

~/.codex·~/.claude에서 가져올 개념

개인 설정의 문구를 복사하지 않고, 여러 하네스에 통하는 구조적 원칙만 비교했어.

개념로컬에서 확인한 형태Lite 판단이유와 적용 위치
공통 asset의 단일 원본 ~/.agents/skills를 공통 영역으로 쓰지만, Claude의 git-master·frontend-ui-ux 복사본은 현재 내용이 달라져 있음 이미 채택 이 drift를 피하려고 Lite는 하나의 skills/를 두 manifest가 직접 공유해. 하네스별 skill 복사본을 만들지 않아.
제품별 runtime 경계 MCP, 권한, hook, agent, 인증·세션은 각 제품 설정에 유지 이미 채택 공통 행동은 skills/, 제품 발견 정보는 .codex-plugin·.claude-plugin, 생명주기는 hooks/로 분리돼.
Host built-in 우선 CLAUDE.md는 built-in이 못 다루는 사용자 정책만 보완 채택 추천 writing-skills에 “두 host가 이미 안정적으로 제공하는 기능은 새 core skill로 복제하지 않는다”는 판단 규칙만 추가하면 돼.
직접 작업이 기본 병렬 fan-out, 문맥 격리, specialist 이득이 분명할 때만 위임 일부 강화 후보 현재도 구현 병렬화는 opt-in이야. SDD trigger에 “직접 구현보다 소유권 분리가 실질적으로 유리할 때”를 더 분명히 쓰면 과호출을 줄일 수 있어.
결과가 달라질 때만 질문 작고 되돌리기 쉬운 변경은 질문 없이 진행 이미 채택 brainstorming이 범위·동작·설계를 바꾸는 결정만 묻고, 명확한 요청에서는 조용히 빠져나와.
위임 brief 계약 Context, Task, Must do, Must not, Verify, Output 구조 이미 채택 Implementer brief가 Outcome, Ownership, Context, Constraints, Verification과 반환 형식을 이미 포함해. 명칭만 다르고 책임은 같아.
검증 상태를 사실대로 분리 통과·실패·미실행과 남은 risk를 구분해 보고 이미 채택 verification-before-completion이 통과 항목, 미검증 항목, 제한을 함께 보고하고 최종 변경 뒤 증거만 인정해.
Incident ratchet 실제 harness 실패로 정책을 바꿀 때 근거 문서를 남김 관리용 후보 사용자 요청마다 로드할 skill은 아니야. 반복 실패가 생길 때만 incidents/에 짧게 기록하는 maintainer 규칙으로 두는 게 가벼워.
Handoff 계약 완료, 미완료, blocker, 검증, 다음 명령을 분리 선택 기능 후보 세션 인계가 잦다면 독립 command나 skill로 유용해. 일반 완료 응답에 강제하면 매번 형식 비용이 생기므로 core에는 넣지 않는 편이 좋아.
Git·commit 규약 git-master와 /commit이 승인, atomic commit, 메시지 형식을 관리 Core 제외 추천 팀마다 규칙이 달라 독립 확장 skill이 적합해. Lite core에는 브랜치 종료 시 안전 경계만 유지하면 충분해.
도메인·도구 전용 skill ast-grep, frontend-ui-ux, using-linear, report-html Core 제외 추천 좋은 skill이지만 범용 방법론이 아니라 선택형 능력이야. 별도 플러그인이나 사용자 전역 skill로 조합하는 편이 Lite 취지와 맞아.
개인·모델 전용 정책 응답 언어, Linear source of truth, 모델 alias, Claude built-in agent, hyperplan 가져오지 않음 사용자 환경이나 특정 host에 결합돼 있어 공개 하네스의 공통 행동으로 만들면 안 돼.
검토 결론

새 core skill을 추가할 필요는 없어. 실제 채택을 검토할 건 Host built-in 우선, SDD 직접 작업 기본을 더 명확히 하기, incident 기록은 runtime 밖에서만 운영하기 세 가지야.

어색한 연결 다이어트 결과

겹치는 trigger와 반복 실행을 줄인 현재 상태야.

발견한 문제다이어트 전현재 동작상태
Brainstorming 오탐 chatter이미 명확해도 불필요하다고 보고명확한 요청이면 아무 말 없이 원래 작업으로 복귀수정
Resume bootstrap 중복이전 문맥이 남은 resume에서도 라우터 본문을 재주입bootstrap은 startup·clear·compact에서만 실행하고 업데이트 확인은 startup에서만 실행수정
Parallel dispatch와 SDD 중복독립 구현 작업이면 두 skill이 모두 넓게 일치구현 소유권은 SDD, 일반 병렬화는 조사·분석 중심으로 분리수정
Subagent 문맥 격리 과잉복잡하다는 이유만으로 모든 작업을 위임할 수 있음대량의 일회성 문맥이나 독립 검증에만 사용하고 결론·증거·위험만 부모가 종합선택적 채택
구현 병렬화 과잉독립 작업이면 자동 병렬 가능코딩 작업 병렬화는 사용자가 명시적으로 요청할 때만 허용수정

Update manager의 skill 노출일시적으로 업데이트 전용 skill이 존재Hook + script 생명주기 경로로 완전히 분리제거

토큰이 사용되는 지점

설치된 skill 전부를 매번 읽지 않아.

항상 들어오는 것

  • Skill 이름과 짧은 description
  • using-superpowers-lite 본문 약 211단어
  • 사용자와 저장소의 현재 지침

조건부로 들어오는 것

  • 실제로 일치한 skill 본문만 로드
  • Debugging reference는 해당 증상일 때만 읽음
  • Subagent implementer prompt는 구현 위임 시에만 읽음
Lite 기준

모든 runtime skill은 500단어 이하로 테스트돼. 선택되지 않은 planning, TDD, review, worktree skill 이름이 runtime skill에서 발견되면 저장소 테스트가 실패해.

기준 파일: hooks/hooks.json, hooks/session-start, hooks/session-update, skills/*/SKILL.md. 로컬 비교 대상: ~/.agents/AGENTS.md, ~/.codex/AGENTS.md, ~/.claude/CLAUDE.md, 사용자 전역 skill·command. 이 문서는 현재 구현을 설명하며 새로운 런타임 규칙을 추가하지 않아.
